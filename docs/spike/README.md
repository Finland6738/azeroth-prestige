# Spike: the probe specification

Milestone M0 answers, in the real WoW Forever client, the questions the design cannot answer offline: the checks V1-V21 of [SPEC-01 §3.3](../specs/SPEC-01-platform-architecture.md) (in Italian). This file is the **specification of the probe addon** `AzPr_Probe`: for every check, the exact calls and events, where to run it, what counts as **go** and what as **revise**, and which spec or ADR each outcome changes. The skeleton (commands, check registry, records, export) is in place since step M0.2; V1 and V19-V21 have their code since M0.3, V2, V3, V12 and V13 since M0.4, V4, V5 and V14 since M0.5, V6-V11, V18 and `L` since M0.6, V15-V17 since M0.7, so that no check is a stub any more ([roadmap](../roadmap/M0-spike.md)); the results go to `docs/spike/M0-results.md` in step M0.9.

## Install

1. Copy `tools/local.example.ini` to `tools/local.ini` (git-ignored) and set `addons` to the `_forever_/Interface/AddOns` folder of your WoW installation.
2. Run:

```bash
python -I -X utf8 tools/install_probe.py
```

3. In game, `/reload` (or restart the client). The chat shows "AzPr Probe: loaded"; `/azpp list` lists the 22 checks.

Run the installer again after every update of the probe, then `/reload`: it replaces the `AzPr_Probe` folder, and the results in `AzPr_ProbeDB` survive. If the client says the addon is out of date, enable "Load out of date AddOns" and note it in the report.

## Rules of the probe

- It lives in `tools/probe/AzPr_Probe/` and is **never distributed**: no release, no `.pkgmeta` entry.
- Every game API call is wrapped in `pcall`. A function that does not exist is recorded as `absent`, never called.
- Every returned value is tested with `issecretvalue` **before** any comparison, arithmetic, indexing or string use. A secret value is recorded as `secret` and dropped.
- It never prints or stores player, guild, channel or realm names, nor GUIDs: only counts, types, field names, `self` / `other`, and booleans such as "matches the group member".
- It uses the test addon-message prefix `AzPrP`, never the real prefix of the addon, and the test channel `AzPrPProbe`, never the addon's channel. Its test messages are capped (50 per burst, at least 0 and at most 5 seconds apart, 255 bytes, 400 per session until `/reload`); a burst stops by command (`/azpp burst stop`) or after 10 refused sends in a row, and the automatic replies to other clients are at most 8 in 10 seconds, so that the probe cannot degrade the service.
- It never touches protected frames in combat and never calls protected functions. Hooks are post-hooks (`hooksecurefunc`, `HookScript`, the official callbacks); it never replaces a Blizzard function. It logs every `ADDON_ACTION_BLOCKED` and `ADDON_ACTION_FORBIDDEN` from login on, under `logs.taint` (the addon only as `self` / `other`).
- It never changes a CVar or a game setting by itself (V16 only reads them and prints the command the owner may type).
- It only listens and asks: it never accepts or turns in a quest, duels, trades, takes or reads a mail (reading marks it read), takes a flight, learns, crafts, posts an auction or queues for a battleground. The requests of M0.6 that reach the client or the server only ask for data: `LegacySystemFrame_LoadUI()` (V7, out of combat), `RequestBattlefieldScoreData()` (V18) and `C_QuestLog.RequestLoadQuestByID(questID)` (`L`); M0.7 adds `C_Calendar.OpenCalendar()` (V15, out of combat). It never ends a cinematic, closes an interaction, releases or resurrects the character.
- It never writes the name of a buyer, sender or opponent either: names the checks need (the winner of a duel, the buyer of an invoice, its own scoreboard row) are compared in memory and dropped; money is written only as above zero or not.

## Names, the API dump and "absent"

The exact names below come from the WoW Forever API dump kept next to this repository (`../WoW-Addons/docs/api.json`, consulted and never copied, [ADR 0002](../adr/0002-wow-forever-target-and-api-dump.md)): version 1.60.1, build 70170, interface 16001, exported on 2026-10-01. The live client may run a different build (SPEC-01 §3.1 says 69913): the probe records `GetBuildInfo()` with every result.

The dump has two parts, and "absent" means different things for each:

- **The documented C API** (systems, functions, events, structures, enumerations): what the client's own `/api` documentation exposes. An event or C function missing there is very likely missing in the client.
- **A snapshot of the global table**, limited to global functions and `C_*` namespaces. Blizzard Lua tables such as `Menu`, `TooltipDataProcessor`, `ChatFrameUtil`, `EventRegistry` and `Enum`, frame methods (`IsForbidden`, `HookScript`, `GetUnit`) and global strings (`ERR_ZONE_EXPLORED`, `DUEL_WINNER_KNOCKOUT`) are **never** in the snapshot, so for them "absent" only means "check at run time".

Two more limits of the dump matter for M0:

- It carries **no secret-value markers**: whether a value is secret in a given context can only be measured in game. The dump does document the `C_Secrets` predicates (`ShouldUnitIdentityBeSecret`, `ShouldUnitComparisonBeSecret`, `CanCompareUnitTokens`, `ShouldAurasBeSecret`, `ShouldUnitAuraInstanceBeSecret`, `HasSecretRestrictions`, ...); the probe records what they predict next to what it observes, so that the real addon can ask them first.
- Several types named in signatures are **not defined** in it: the enumerations `SendAddonMessageResult`, `RegisterAddonMessagePrefixResult`, `AddOnRestrictionType`, `AddOnRestrictionState`, `PlayerInteractionType`, `GameMode`, `GameRule`, and the structures `AuraData` and `UnitAuraUpdateInfo`. The probe reads them at run time (every key and value of `Enum.<Name>`, every field of a returned table) and stores their shape.

In the checks below, a name followed by *(not in the dump)* is one the dump does not list; everything else is in the dump.

## Where to run: contexts

| Tag | Context |
|---|---|
| **W** | Open world, out of combat (a city counts as W) |
| **WC** | Open world, in combat (a mob is enough; with another player around when the check says so) |
| **D** | Inside a dungeon, out of combat |
| **DB** | During a dungeon boss encounter (between `ENCOUNTER_START` and `ENCOUNTER_END`) |
| **R** / **RB** | Inside a raid (Barrow Deeps is the smallest) / during a raid boss |
| **BG** | Inside a battleground (Darkspear Islands), during the match and at its end |
| **2C** | Needs a second client or a second player running the probe (**2CX**: of the opposite faction) |
| **HC** | Needs a character on a Hardcore realm |
| **LS** | Across a loading screen (entering and leaving an instance) |

Each check stores one log line per context it was run in, tagged with the context the probe detects by itself (`IsInInstance()`, `GetInstanceInfo()`, `InCombatLockdown()`, `C_InstanceEncounter.IsEncounterInProgress()`, `C_PvP.IsBattleground()`). A check is `pass` only when all its required contexts are covered.

## Commands

| Command | What it does |
|---|---|
| `/azpp` or `/azpp list` | Lists the checks V1-V21 (plus `L` for content levels) with a short description, the contexts still missing and the last result |
| `/azpp run <id>` | Runs one check now in the current context, for example `/azpp run V3`. Checks that need an event (an encounter, a turn-in, a match end) arm a watcher and complete when the event arrives; the chat line says so |
| `/azpp export` | Opens a movable frame with every result and every log as plain text, already selected: press Ctrl+C and paste it into the *In-game test report* issue form |
| `/azpp reset` | Asks for confirmation: `/azpp reset confirm` clears every result and log (never needed between the contexts of one check) |
| `/azpp help` | Lists the commands of the installed version |
| `/azpp assist [seconds\|stop]` | (M0.3, V21) Scans the visible plates twice a second for `seconds` (default 60, at most 300), so that V21 is measured in combat without typing; `stop` ends the window early. It ends with a summary line and records V21 |
| `/azpp surfaces [plates\|tooltip\|menu\|chat\|all on\|off]` | (M0.4, V3, V12, V13) Without arguments, shows which badge surfaces of the probe are on; with a surface (or `all`) and `on` / `off`, switches it. All are on by default and the setting survives `/reload` (`AzPr_ProbeDB.switches`). `chat off` removes the filter; `plates off` hides the test textures (after combat, if one is anchored to a protected plate); the tooltip post-call and the menu callbacks cannot be unregistered, so when off they return at once and add nothing |
| `/azpp ping <dist>` | (M0.5, V4) One ping on `<dist>`: `guild`, `party`, `raid`, `instance` (`INSTANCE_CHAT`), `whisper <name>` or `channel` (the test channel, joined first). Every client running the probe answers with a pong on the same distribution (to a whisper, by whisper), and the sender logs the round trip in milliseconds and whether the pong came from the same or the opposite faction |
| `/azpp pong [on\|off]` | (M0.5, V4) Switches the automatic pong replies (on by default; the setting survives `/reload`) |
| `/azpp burst <dist> [n] [gap] [bytes]` | (M0.5, V4) `n` messages (default 10, at most 50) every `gap` seconds (default 0, at most 5) of `bytes` bytes (default 200, 40 to 255), each result code counted; then an end marker, which the other clients acknowledge with what they received. `/azpp burst stop` ends it early. One summary line per burst: codes, the first refusal and after how many milliseconds, own echoes, acknowledgements |
| `/azpp size <dist>` | (M0.5, V4) Six messages of 100, 200, 254, 255, 256 and 300 bytes, half a second apart, with the result code of each; the receivers report the longest message that arrived intact |
| `/azpp channel join\|leave\|status\|count` | (M0.5, V4) `join` joins the hidden test channel `AzPrPProbe` with `JoinTemporaryChannel` (out of combat), hides its notices and removes it from every chat frame 3 seconds later, then checks the frames again; `leave` leaves it with `LeaveChannelByName`; `status` logs its number, the chat frames that list it and the member count; `count` also asks for the roster and counts its entries |
| `/azpp lockdown [auto on\|off]` | (M0.5, V5) A lockdown snapshot followed by one test send per distribution available here (guild, party or raid, instance, test channel, a whisper to the probe character itself), each result compared with the flag. `auto on` repeats it by itself 5 seconds after `ENCOUNTER_START`, 3 seconds after `PLAYER_REGEN_DISABLED` and 1 second after the end of a lockdown (at most once every 30 seconds; off by default, the setting survives `/reload`) |
| `/azpp encsend <dist>` | (M0.5, V14) Sends the invented 2 KB profile, serialized to CBOR, compressed with Deflate and encoded in Base64, in chunks of 200 characters one second apart; the other client decodes it, compares it with the same profile built locally and acknowledges `ok` or what failed |
| `/azpp msgs` | (M0.5) Prints the message counters: result codes, messages received, lockdown flags per context, the session's test messages and the switches |
| `/azpp legacy watch [seconds]\|stop` | (M0.6, V7) For `seconds` (default 30, from 5 to 300) registers one frame for every event and logs those whose name contains `LEGACY`, `ACHIEVEMENT` or `CRITERIA` (names and payload shapes). Out of combat only; it ends by itself when a fight starts |
| `/azpp uiwatch flight\|boat\|zeppelin\|panels [seconds]\|stop` | (M0.7, V15) Once a second for `seconds` (default 300, from 30 to 900) reads the signals of a transport and the UI panels, under the label typed (what the owner is riding); `stop` ends it |
| `/azpp cvar [name]` | (M0.7, V16) Prints, for each candidate CVar the client knows, the `/console` commands the owner types to force it and to set it back; with a name, adds it to the candidates if the client knows it |
| `/azpp hardcore yes\|no` | (M0.7, V17) The owner says whether this character is on a Hardcore realm, so that the probe can tell a wrong flag; remembered until `/reload`, never stored |

Steps M0.3-M0.7 add the helper commands their checks need; they are documented in this file by those steps, and `/azpp help` always lists the ones the installed version has. A character name typed in a command is used once and never stored (during a burst to a whisper target it stays in memory until the burst ends).

## Record format

The probe saves everything in the SavedVariable `AzPr_ProbeDB`:

```lua
AzPr_ProbeDB = {
  schema = 1,
  results = {
    V1 = { id = "V1", result = "pass", details = "DB 3 kills, RB 1 kill: 5/5 fields readable; BOSS_KILL after END",
           build = "1.60.1 70170 16001", time = 1764300000 },
  },
  logs = {
    V1 = { "DB | ENCOUNTER_END | encounterID=number encounterName=string difficultyID=number groupSize=number success=number encounterUnitStatus=table" },
  },
  covered = {
    V1 = { DB = true },
  },
  stats = {
    V1 = { starts = 4, ends = 4, bossKills = 3, ctx = { DB = { ends = 4, kills = 3, wipes = 1 } } },
  },
}
```

`covered` holds the contexts each check has been run in, apart from the logs, so that the cap on the logs never loses them; `/azpp list` shows the required ones still missing. `stats` (since M0.3) holds the counters a check adds up across contexts and sessions (for example `stats.V1.ctx.DB.kills`, `stats.V20.ctx.WC.srcSecret`): numbers and tallies only, never a name; the result of the check is computed from them. A check that raises an error records `info` with the `error:` text; an error inside an event handler or a timer is logged under `logs.errors`.

| Field | Content |
|---|---|
| `id` | The check id: `V1` … `V21`, or `L` (content levels, part of M0.6) |
| `result` | `pass`: the go criteria hold in every required context. `fail`: at least one revise condition was observed. `info`: data recorded, the decision needs a human reading (M0.9). `todo`: not implemented yet, or required contexts not run yet (they are listed in `details`) |
| `details` | One line, at most 240 characters: counts, shapes and the contexts covered or missing. Never a name |
| `build` | `GetBuildInfo()` as `"<version> <build> <interface>"` |
| `time` | `time()` when the record was written (seconds since the epoch) |

Values in logs are written as **shapes**: `number`, `string`, `boolean`, `table(<n> keys)`, `nil`, `secret`, `absent` (the function does not exist), `error: <first 80 characters>` (the `pcall` failed). Numbers that carry no personal data (ids, levels, counts, result codes, milliseconds) are written as values. Logs are capped at 200 lines per check, oldest dropped first. The export frame prints one line per result (`V1 | pass | <details> | <build> | <time as UTC ISO date>`), then the logs.

## M0.3: encounters, group levels and auras

### V1: `ENCOUNTER_END` with readable values

- **Calls and events:** `ENCOUNTER_START(encounterID, encounterName, difficultyID, groupSize)`; `ENCOUNTER_END(encounterID, encounterName, difficultyID, groupSize, success, encounterUnitStatus)` (the dump adds `encounterUnitStatus`, a table the spec does not know: record its shape); `BOSS_KILL(encounterID, encounterName)` and its order and delay relative to `ENCOUNTER_END`; `issecretvalue` on every payload field and on every field of `encounterUnitStatus`; `C_InstanceEncounter.IsEncounterInProgress()`; `GetInstanceInfo()` (`instanceType`, `difficultyID`, `maxPlayers`, `instanceID`); `UnitIsAFK(unit)` and `UnitIsConnected(unit)` for `party1..4` / `raid1..40` at `ENCOUNTER_END`; `C_Secrets.HasSecretRestrictions()`. Fallback sources measured at the same time: `UPDATE_INSTANCE_INFO` with `GetNumSavedInstances()` / `GetSavedInstanceInfo(index)`, `C_RaidLocks.IsEncounterComplete(...)`, `ENCOUNTER_LOOT_RECEIVED`, `CHAT_MSG_SYSTEM` (count only).
- **Where:** DB (a kill and, if it happens, a wipe), RB (at least one kill), across LS (does an encounter survive a disconnect or reload?).
- **Go:** `ENCOUNTER_END` arrives once per pull in dungeons and raids; the five spec fields are never secret; `success` is `1` on a kill and `0` on a wipe; `encounterID` is the same as `BOSS_KILL`'s and stable across runs; `UnitIsAFK` of group members is readable at that moment.
- **Revise:** any of the five fields secret, the event missing in a context, or `success` unreliable: Delver moves to `BOSS_KILL` plus the saved-instance or raid-lock state; `UnitIsAFK` secret: the "not AFK" eligibility is measured another way or dropped.
- **Changes:** [SPEC-03 §7.2](../specs/SPEC-03-activity-catalog.md) (Delver source and eligibility), [SPEC-02 §8.6.2](../specs/SPEC-02-progression-scoring.md) (the boss window `ENCOUNTER_START`..`END`), [SPEC-09 §15.3](../specs/SPEC-09-celebrations.md) (encounter blocking condition), risk R1 of [SPEC-11](../specs/SPEC-11-risks-open-questions.md); a Delver redesign gets a new ADR.
- **How the probe runs it (M0.3, `Checks_Encounters.lua`):** the events are watched from login on, so there is nothing to arm: just play. `ENCOUNTER_START`, `ENCOUNTER_END` and `BOSS_KILL` each log one line with every payload field (numbers as values, strings as `string`, `encounterUnitStatus` by shape: keys, field names, value types, secret count), tagged `enc=DB` or `enc=RB` from the instance type; `ENCOUNTER_END` adds a second line with `UnitIsAFK`, `UnitIsConnected` and `UnitIsDeadOrGhost` of the player and of every member as tallies, `IsEncounterInProgress`, `HasSecretRestrictions` and `GetInstanceInfo()` without the name. The open encounter is kept in `stats`, so a loading screen or `/reload` during a pull is logged (`PLAYER_ENTERING_WORLD`, then the state 5 seconds later) and counted as `LS` when the encounter ends (or never does). After a kill the probe also logs `C_RaidLocks.IsEncounterComplete(instanceID, encounterID, difficultyID)`, calls `RequestRaidInfo()` and logs the shape of the saved instances at `UPDATE_INSTANCE_INFO`, and counts `CHAT_MSG_SYSTEM` (and how many of them are secret) and `ENCOUNTER_LOOT_RECEIVED` (shapes only: a field may hold a player name) for 10 seconds. `BOSS_KILL` is paired with the `ENCOUNTER_END` within 10 seconds, before or after, and the delay and the ids are compared. Every `ENCOUNTER_END` records V1 and prints one chat line. `/azpp run V1` logs a snapshot (open encounter, state, kills by encounter id) and the summary. **Result:** `fail` as soon as one of the five spec fields was secret, `success` was not 0 or 1, the `BOSS_KILL` id differed, a `BOSS_KILL` came without `ENCOUNTER_END`, an `ENCOUNTER_END` came twice, `UnitIsAFK` was secret or an encounter was lost across a loading screen; `pass` when none of these happened, DB, RB and LS are covered and there is at least one kill in DB and one in RB; `todo` otherwise.

### V19: `UnitLevel` of group members and of far higher hostile players

- **Calls and events:** `UnitLevel(unit)` for `player`, `party1..4`, `raid1..40`, `target` and hostile `nameplateN` players; `issecretvalue` on the level; `UnitIsPlayer`, `UnitIsConnected`, `UnitInParty`, `UnitInRaid`, `IsInGroup`, `IsInRaid`, `GetNumGroupMembers`; `GROUP_ROSTER_UPDATE`, `UNIT_LEVEL(unitTarget)`, `PLAYER_LEVEL_UP(level, ...)`; the delay between `GROUP_ROSTER_UPDATE` and the first valid level of a new member (levels read 0, 1 and 3 seconds later).
- **Where:** W with a group member at least 10 levels higher, near, far (another zone) and offline; D, R and BG with the same group; W on a PvP realm (or BG) with a hostile player far above the probe character.
- **Go:** the level of every group member is a non-secret number in every context, also far away and offline, and valid within 1 second of the roster event; a hostile player 10 or more levels higher returns `-1`.
- **Revise:** levels secret, `0` or missing for far or offline members: trigger G uses the last level seen (cached per GUID) or the level the member's own client reports; `-1` never returned (or returned for other reasons): the A1 rule cannot treat `-1` as "+10".
- **Changes:** [SPEC-02 §8.6.1](../specs/SPEC-02-progression-scoring.md) (trigger G, the note on `-1`), §8.6.3 (`c.gmx` recomputed by peers), `Domain/Boost.lua` (M1.9).
- **How the probe runs it (M0.3, `Checks_AntiBoost.lua`):** `/azpp run V19` in each context, with the group formed: it reads `UnitLevel` of every member, sorted by where the member is (`near` = `UnitIsVisible`, `far` = connected but not visible, `offline` = `UnitIsConnected` false) and by what the level is (`valid`, `zero`, `minus1`, `negative`, `secret`, `nil`, `error`), counts the members 10 or more levels above the player, and reads `target` and `nameplate1..40` for hostile players (`UnitIsPlayer` and `UnitCanAttack`): `-1`, readable and 10+ higher, readable and closer. The run covers the context when the player is in a group. From login on, `GROUP_ROSTER_UPDATE` logs the group size and the delay since the previous one; when the group grows, the levels are read again 0, 1 and 3 seconds later; `UNIT_LEVEL` logs the level of the player and of group members with the delay since the roster event; `PLAYER_LEVEL_UP` logs the new level next to `UnitLevel("player")`. **Result:** `fail` when a member level was secret, 0 or -1 (in a run or 3 seconds after a roster change), invalid 1 second after a roster change, a hostile player 10+ higher was readable instead of `-1`, or a non-hostile player returned `-1`; `pass` when none of these happened, W, D, R and BG are covered, a +10 member was seen near, far and offline and a hostile `-1` was seen; `todo` otherwise.

### V20: `sourceUnit` of the auras on the player

- **Calls and events:** `UNIT_AURA(unitTarget, updateInfo)` for `player` (shape of `updateInfo`, *`UnitAuraUpdateInfo` not in the dump*: `addedAuras`, `isFullUpdate`, ...); `C_UnitAuras.GetAuraDataByAuraInstanceID("player", auraInstanceID)`, `C_UnitAuras.GetAuraDataByIndex("player", index, "HELPFUL")`, `C_UnitAuras.GetPlayerAuraBySpellID(spellID)`; the fields `sourceUnit`, `isFromPlayerOrPlayerPet`, `spellId` of the returned aura (*`AuraData` not in the dump*), each through `issecretvalue`; `C_Secrets.ShouldAurasBeSecret()` and `C_Secrets.ShouldUnitAuraInstanceBeSecret("player", auraInstanceID)` next to the observation; for a readable source, `UnitInParty(sourceUnit)`, `UnitIsPlayer(sourceUnit)` and `UnitLevel(sourceUnit)`.
- **Where:** W (a buff from a player outside the group, out of combat), WC (a heal or buff from a player outside the group while the probe character fights), D and DB for contrast. Needs a helper: 2C or a willing stranger.
- **Go:** in the open world, in and out of combat, `sourceUnit` of a helpful aura cast by another player is readable and its level can be read.

## M0.5: addon messages and encoding

All three checks live in `Checks_Messaging.lua` (M0.5). The probe registers the test prefix `AzPrP` at `PLAYER_LOGIN` and sends only with it. Every test message has the form `<kind>|<token>|<run>|<seq>|<arg>|<faction>|<rest>`: `<token>` is four random hex digits drawn at each login, so the probe recognises its own messages (the echoes of `GUILD`, `PARTY`, `RAID`, `INSTANCE_CHAT` and `CHANNEL`) without comparing any name; `<faction>` is `A`, `H` or `N`, so the receiver tells same-faction from cross-faction delivery; the kinds are `PI` / `PO` (ping, pong), `BU` / `BE` / `BA` (burst message padded to a declared length, end marker with the number accepted, acknowledgement with the number received, intact and the longest), `LK` (lockdown test, with the sender's context and flag) and `EN` / `EA` (encoded chunk, acknowledgement). Every result of `SendAddonMessage` is written by its `Enum.SendAddonMessageResult` key (the number when the key is unknown, `true` / `false` when the client returns a boolean, `error` when the call raises, for example above 255 bytes) and classed `ok`, `throttle`, `lockdown` or `refused`; codes are counted per distribution and per context. The sender of a message is never stored: it is passed once to the pong or acknowledgement of a whisper. The other clients' replies (pong, acknowledgements) are at most 8 in 10 seconds.

### L: content levels (risk R13)

Not a V check, but part of M0.6: the level `L` of a boss, a quest and a zone that the scoring uses.

- **Calls and events:** bosses: `UnitLevel("boss1")` to `UnitLevel("boss5")` and `UnitLevel("target")` during an encounter (a number, `-1` or secret?), `UnitEffectiveLevel`, `UnitClassification`, `C_PlayerInfo.GetContentDifficultyCreatureForPlayer`; `C_EncounterJournal.GetEncountersOnMap(uiMapID)`, `C_EncounterJournal.GetInstanceForGameMap`, `EJ_GetInstanceInfo`, `EJ_GetEncounterInfo` and `EJ_GetEncounterInfoByIndex` (do they give a level or a recommended range?); quests: `C_QuestLog.GetQuestDifficultyLevel(questID)` for quests in the log, after the turn-in and for completed quests (before and after `C_QuestLog.RequestLoadQuestByID`), `C_PlayerInfo.GetContentDifficultyQuestForPlayer`, `UnitQuestTrivialLevelRange`; zones and instances: `C_Map.GetMapLevels(uiMapID)` (returns `playerMinLevel`, `playerMaxLevel`), `GetInstanceInfo()` with `GetLFGDungeonInfo(lfgDungeonID)` (minimum, maximum and recommended levels) and `C_LFGInfo.GetDungeonInfo`.
- **Where:** W (quests, zones), DB and RB (bosses).
- **Go:** each kind of content has a client source that gives a stable level.
- **Revise:** no source for a kind: hand-curated tables in the ruleset, written from what the client shows in game (never copied from third-party databases), in step M2.2.
- **Changes:** [SPEC-03 §7](../specs/SPEC-03-activity-catalog.md) (the convention on `L`), risk R13.
- **How the probe runs it (M0.6, `Checks_Levels.lua`):** bosses are read 2 and 10 seconds after `ENCOUNTER_START`, at `INSTANCE_ENCOUNTER_ENGAGE_UNIT` and at `/azpp run L` (the boss units; the target only when it is not a player, and as a boss only during an encounter without boss units); quests 1 second after `QUEST_ACCEPTED` and `QUEST_TURNED_IN`, and at the run the quests of the log and 5 completed ones whose data it requests; zones and instances 5 seconds after a loading screen or `ZONE_CHANGED_NEW_AREA`, and at the run, with the levels of the continent's zones, the LFG data and the encounter journal of the instance. Each level is counted per kind as valid (above 0), `-1`, 0 or secret; the level of a quest, a zone or a boss of an encounter is remembered (up to 100) and counted as changed when it differs. **Result:** `fail` when a boss, quest or zone level was secret, none of a kind that was read was valid, or a level changed; `pass` when none of these happened, W, DB and RB are covered and each of the three kinds has a valid level; `todo` otherwise. ### V16: a CVar that forces the restrictions

- **Revise:** none: restricted-state checks in later milestones use real content (a training dummy, a dungeon boss).
